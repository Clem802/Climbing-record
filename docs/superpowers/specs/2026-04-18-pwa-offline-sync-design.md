# PWA + Offline Sync — Design Spec
Date: 2026-04-18

## Overview
Convert the climbing boulder tracker into a Progressive Web App with full offline-first support. All session actions (create, update, delete) are queueable offline and sync when connectivity returns. Conflicts are surfaced to the user for manual resolution.

---

## Architecture

### Service Worker
Generated by `vite-plugin-pwa` (Workbox under the hood).

- **Static assets** — CacheFirst strategy; JS, CSS, fonts, icons cached on install
- **`/api/*` requests** — NetworkFirst strategy; response cached on success, served from cache when offline
- **`sync` event** — fires when connectivity returns; triggers queue drain via a message to the app

### Sync Queue (IndexedDB)
Database name: `boulder-sync`  
Object stores:
- `queue` — pending/conflict/error actions
- `sessions-cache` — last-known good API responses for offline reads

Queue entry shape:
```js
{
  id: string,          // uuid
  type: 'CREATE_SESSION' | 'UPDATE_SESSION' | 'DELETE_SESSION',
  payload: object,     // full data needed to replay the action
  timestamp: number,   // ms since epoch — when the action was queued
  status: 'pending' | 'conflict' | 'error'
}
```

Queue is drained oldest-first. A DELETE entry for a session that has a pending CREATE is coalesced — both are dropped.

### Conflict Detection
- `sessions` table gains an `updated_at TIMESTAMPTZ` column (added via migration)
- All session API responses include `updated_at`
- On sync, each queue entry's `timestamp` is compared to the server's `updated_at` for that session
- If `server.updated_at > entry.timestamp` → mark entry `conflict`

### Local Session Cache
On every successful `/api/sessions` fetch, responses are written to the `sessions-cache` store. Offline reads come from here. Optimistic entries (queued but unconfirmed) are merged in at read time with an `unsynced: true` flag.

## Data Flow

### Offline session creation
1. User submits session form → `useOfflineQueue.createSession(data)`
2. **Online** → POST `/api/sessions`, cache response in IndexedDB, return result
3. **Offline** → write `CREATE_SESSION` entry to queue, write optimistic session to `sessions-cache` with `unsynced: true`, return optimistic result to UI
4. On reconnect → service worker fires `sync` → hook drains queue oldest-first → compares timestamps → resolves or flags conflicts

### Conflict resolution
- `ConflictResolver` modal blocks UI until all conflicts cleared
- **Keep mine** → PUT local version with current timestamp, remove from queue
- **Keep server** → discard queue entry, update `sessions-cache` with server version

## Error Handling & Edge Cases

| Scenario | Behaviour |
|----------|-----------|
| Network error mid-sync | Entry stays `pending`, retries on next reconnect |
| 4xx on sync (e.g. session deleted server-side) | Entry marked `error`, shown with "Discard" option |
| Safari (no `beforeinstallprompt`) | InstallPrompt shows manual "tap Share → Add to Home Screen" instruction |
| DELETE queued for session with pending CREATE | Both entries coalesced and dropped — no network call needed |
| App force-closed before sync | Queue persists in IndexedDB, drained on next open |
| Conflict modal open, user creates another session | New session queued normally; conflict modal must be resolved before further syncs run |

## Dependencies
- `vite-plugin-pwa` (devDependency in client)
- `workbox-window` (peer of vite-plugin-pwa)
- `idb` — thin IndexedDB wrapper (client dependency)

No server-side dependencies beyond the `updated_at` migration.

---

## Out of Scope
- Push notifications
- Background sync for non-session data (admin, user profile)
- Offline support for the Progress charts page (read-only, served from cache automatically via NetworkFirst)
